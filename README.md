1. Présentation du projet Mbongo Pharma aide les habitants de Brazzaville et Pointe-Noire à savoir, avant de se déplacer, quelle pharmacie a leur médicament en stock et quelle pharmacie est de garde. Les pharmacies mettent à jour leur stock en quelques clics. L'information publique reste rapide, même sur une connexion mobile limitée. Principe fondamental : l'application indique où trouver un médicament, jamais quoi prendre. Aucun conseil médical, aucun dosage. Stack technique Élément Choix Framework Style Next.js (App Router, TypeScript) Tailwind CSS Authentification Auth.js (Credentials, session JWT) Base de données PostgreSQL hébergé sur Neon, via Prisma Hébergement Utilisateurs Vercel (déploiement automatique depuis main) • Visiteur : aucun compte nécessaire. Il cherche, consulte, filtre. • Pharmacie (rôle PHARMACY) : gère son stock et son profil. • Administrateur (rôle ADMIN) : valide les pharmacies et saisit les gardes.

2. Comprendre les termes techniques Le rendu répond à une seule question : à quel moment la page HTML est-elle fabriquée ? Imaginez une boulangerie : on peut préparer les sandwichs le matin pour tout le monde, les refaire toutes les heures, ou les préparer à la commande. Chaque méthode a ses avantages.

2.1 Les quatre modes de rendu Sigle Nom complet Explication simple Dans Mbongo Pharma SSG ISR Static Site Generation Incremental Static Regeneration La page est fabriquée une seule fois, au moment du déploiement (le « build »). Ensuite, chaque visiteur reçoit la même page toute prête. C'est le plus rapide. Image : des sandwichs préparés le matin. Limite : elle ne change pas avant le prochain déploiement. Accueil, « Comment ça marche », « Pour les pharmacies » Une page statique qui se renouvelle toute seule. Soit après un délai (revalidate = 60 : toutes les 60 s), soit à la demande (revalidatePath : on force la mise à jour quand les données changent). Rapide comme le SSG, mais jamais trop périmée. Image : des sandwichs refaits toutes les heures. /pharmacies (60 s), /pharmacies-de-garde (300 s), /pharmacies/[slug] (à la demande) SSR CSR Server-Side Rendering Client-Side Rendering La page est fabriquée par le serveur à chaque visite, avec les données du moment. Toujours à jour et personnalisable, mais un peu plus lent et plus coûteux. Image : un plat préparé à la commande. /recherche?q=, /pharmacie/stock, /admin Le navigateur du visiteur construit la page avec du JavaScript. Pratique pour l'interactivité, mais pénible sur un téléphone modeste ou une connexion lente. On le limite aux boutons et formulaires ("use client"). 

2.2 Comment choisir entre SSG, ISR et SSR ? Formulaires, boutons interactifs 
  1. La page change à chaque visite ou dépend de l'utilisateur ou de l'URL ? SSR.
  2. Sinon, ses données changent de temps en temps et doivent rester assez fraîches ? ISR.
  3. Sinon, elle ne change presque jamais ? SSG. Dans le README, la section « Rendu » doit expliquer ce raisonnement pour         chaque page : le choix compte autant que le code.
